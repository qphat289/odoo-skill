1. Skill, agent, workflow, rule là gì?

Muốn dùng bộ này hiệu quả, cả team cần phân biệt rõ vai trò của từng lớp. Mỗi lớp có chức năng riêng. Không nên trộn chúng vào một file duy nhất.

Skill

Gói điều hướng và kiến thức. Skill chỉ cho agent phải đọc gì trước, dùng version nào, và tham chiếu file nào.

Workflow

Playbook cho từng loại việc. Ví dụ: tạo module, review module, nâng version module.

Rule

Ràng buộc bắt buộc. Ví dụ: security, coding style, manifest order, version-specific constraints.

Agent

Helper prompt theo vai trò. Ví dụ: planner, reviewer, tester, upgrade analyzer.

Điểm quan trọng: skill không thay workflow. Workflow không thay rule. Agent không thay source-of-truth.

2. Ví dụ cách mọi thứ hoạt động cùng nhau

Ví dụ: user yêu cầu “Tạo sales approval module cho Odoo 18”. Agent không nên nhảy vào code ngay. Nó phải đi qua một chuỗi bước rõ ràng.

1

Detect version

Biết chính xác đây là Odoo 18. Nếu chưa rõ thì dừng và xác nhận.

2

Load router skill

Đọc SKILL.md và shared router skill.

3

Switch version skill

Chuyển sang skills/odoo-18.0/ để dùng syntax và patterns đúng.

4

Load workflow

Đọc workflows/generate-module.md để biết thứ tự làm việc.

5

Apply rules

Áp rules/security.md và rules/coding-style.md.

6

Call helper agent

Nếu task phức tạp thì đọc thêm planner, reviewer hoặc tester agent.

User requestTạo sales approval module cho Odoo 18
→
Skill routerChọn version skill, references, workflow phù hợp
→
ExecutionCode theo workflow, có rules và review checkpoints
Nếu không dùng cấu trúc này, agent rất dễ code theo memory và lẫn syntax giữa các version.

3. AGENTS.md làm sao cho hiệu quả?

AGENTS.md nên là file điều phối ở mức project. Nó không cần nhồi toàn bộ kiến thức Odoo. Nó cần nói rõ repo này là gì, agent phải đọc gì trước, và hard rules nào luôn phải nhớ.

AGENTS.md của repo này có 3 phần chính

Meaning
Giải thích repo gồm router skill, version skills, knowledge base, workflows, rules, agents và scripts.
Required workflow
Bắt agent đi đúng thứ tự: detect version, đọc skill, chọn workflow, đọc references, áp rules.
Odoo rules
Giữ các hard rules ngắn gọn như version phải rõ, attrs cho 17+, Command cho 16+, access rights bắt buộc.

Nguyên tắc viết AGENTS.md tốt

  • Ngắn, rõ, chỉ giữ phần điều phối và hard rules.
  • Trỏ đúng source-of-truth thay vì copy lại nguyên nội dung của skill hoặc references.
  • Nói rõ “đọc gì trước, đọc gì sau”.
  • Không nhét chi tiết version table dài vào đây nếu đã có version skills riêng.
Khung tư duy khi viết AGENTS.md: 1. Repo này là gì? 2. Agent phải đọc file nào trước? 3. Khi nào phải switch sang version skill? 4. Rules nào luôn phải áp? 5. Trước khi finish phải validate gì?

4. Khi code, sửa, review thì nên dùng như thế nào?

Cách dễ nhớ nhất là: task rộng thì gọi skill. Task hẹp, vai trò rõ thì gọi agent chuyên trách.

Nên gọi skill trực tiếp khi

  • Tạo mới module hoặc feature
  • Sửa bug functional hoặc technical
  • Muốn agent tự chọn đúng reference và workflow
  • Muốn đi full pipeline từ hiểu bài đến output cuối

Nên gọi agent cụ thể khi

  • Chỉ cần plan
  • Chỉ cần review security hoặc style
  • Chỉ cần test strategy
  • Chỉ cần phân tích upgrade impact

Code mới

Gọi skill trước. Nêu rõ version, task, output mong muốn.

Sửa code

Vẫn gọi skill nếu bug liên quan flow hoặc version. Chỉ gọi agent riêng nếu task rất hẹp.

Review code

Có thể gọi skill hoặc gọi thẳng reviewer agent nếu mục tiêu chỉ là audit.

Ví dụ prompt ngắn: Use the Odoo development skill for Odoo 18. Review this module for security, style, and version-specific issues. List findings first, then suggest fixes.

5. SETUP.md dùng để làm gì? Prompt agent sao để setup cho chuẩn?

SETUP.md là playbook cài đặt cho agent khác đọc và làm theo. Nó giúp agent không tự đoán host, không tự đoán path, và không cài thiếu support folders.

Vai trò chính của SETUP.md

  • Phân biệt native skill host và project-instruction host
  • Chỉ rõ path cài đặt, scope cài đặt, wrapper script cần dùng
  • Buộc agent validate sau khi cài
  • Cho smoke test ngay sau setup

Prompt setup mẫu

Dùng file SETUP.md trong repo này và setup bộ Odoo skill cho IDE của tôi là Codex. Ưu tiên native install nếu host có hỗ trợ. Sau khi setup xong, kiểm tra lại skill path, support folders, và cho tôi 1 prompt smoke test để dùng ngay.

7. Flow dùng hằng ngày cho team

Nếu muốn áp dụng thực tế, đây là flow ngắn gọn mà team có thể dùng mỗi ngày.

A. Trước khi code

  • Xác định Odoo version
  • Đọc router skill
  • Chọn workflow đúng
  • Đọc references cần thiết

B. Trong lúc code

  • Code theo plan
  • Không bỏ qua security
  • Không viết theo memory
  • Giữ output theo đúng module structure

C. Trước khi giao

  • Review theo reviewer agent hoặc workflow review
  • Check manifest order
  • Check syntax theo version
  • Check test và warnings
Prompt daily use: Use the Odoo development skill for Odoo 18. Create spec first, then plan, then scaffold the module. After coding, run a security and style review before final output.

8. Nếu agent code sai thì chỉnh skill như thế nào cho chuẩn?

Khi agent sai, đừng chỉ vá ở prompt của một lần chạy. Hãy sửa đúng source-of-truth để lần sau agent tự né lỗi đó.

Sửa rule

Nếu lỗi là ràng buộc cứng, ví dụ thiếu access rights hoặc sai manifest order, hãy thêm hoặc chỉnh rule.

Sửa reference

Nếu lỗi do thiếu kiến thức, ví dụ pattern XML hoặc multi-company handling, hãy sửa file reference đúng chỗ.

Sửa workflow

Nếu lỗi do agent làm sai thứ tự, ví dụ code trước khi có plan, hãy sửa workflow hoặc checklist execution.

Cách nghĩ nhanh

  • Lỗi chung, bắt buộc: sửa rules/
  • Lỗi theo version hoặc domain: sửa reference hoặc version skill
  • Lỗi do sai thứ tự làm việc: sửa workflow
  • Lỗi chỉ xuất hiện lúc audit: sửa reviewer hoặc checklist review

Common bug lặp lại thì làm sao?

  • Nếu bug lặp nhiều lần, gom nó thành checklist tái sử dụng
  • Đặt ở chỗ dễ áp nhất, thường là rules/common-bugs.md
  • Buộc reviewer hoặc workflow cuối đọc file này trước khi finish
  • Chỉ tạo file riêng khi nhóm bug đủ ổn định và dùng lại được

Mẫu gọn để xử lý common bug

rules/ common-bugs.md Trong file: - tên lỗi - version ảnh hưởng - cách đúng - check nhanh trước khi finish
Nguyên tắc: không tạo file riêng cho mọi lỗi. Chỉ tạo khi lỗi đó lặp lại đủ nhiều để trở thành checklist dùng lại.
Ví dụ prompt nâng chất lượng repo: We keep hitting the same Odoo 18 mistakes with access rights, manifest order, and XML syntax. Update the skill pack so these common bugs are caught earlier. If needed, add a reusable common-bugs checklist in the right place and wire it into the review workflow.

9. Kết luận cho team

Cách dùng bộ skill này hiệu quả nhất là coi nó như một operating system cho Odoo work, không chỉ là một folder markdown để tham khảo.

Best practice

  • Bắt đầu từ skill, không bắt đầu từ “code luôn”
  • Version phải rõ ngay từ đầu
  • Task lớn thì dùng full pipeline
  • Task nhỏ, vai trò rõ thì gọi agent chuyên trách
  • Khi agent sai, sửa source-of-truth chứ không chỉ sửa prompt tạm

Prompt mở đầu workshop demo

Use the Odoo development skill for Odoo 18. Take this requirement, create a short spec, then a plan, then scaffold the demo module and run a review checklist before final output.

Chỉ cần team thống nhất cách gọi skill và cách sửa source-of-truth, chất lượng output sẽ tăng dần theo thời gian.
